# Clarivue AI

**Clarity in Every Creation. Consistency in Every Brand.**

AI-powered brand-governance platform that checks organisational content against approved brand guidelines before publication.

Built by **TECHORY** for the Inkloom AI Hackathon — Round 2.

## Status

Phase 1 complete: project scaffolding, environment setup, and a verified end-to-end health check between frontend, backend, and MongoDB.

Phase 2 complete: MongoDB data models, repository layer, indexes, and the Nova Electronics seed data.

Phase 3 complete: Brand Guideline Management -- PDF upload/extraction/chunking, brand facts/terminology/claim-policy/asset CRUD, and the admin dashboard described below.

> **⚠️ Demo-only organisation context.** There is no real authentication yet. The frontend sends the active organisation and user as plain `X-Organisation-Id` / `X-User-Id` request headers (chosen from a dropdown in the sidebar), and the backend only checks that both exist and belong together (`app/core/demo_context.py`). **This is not production authentication or security** -- real auth replaces this mechanism in a later phase.

## Brand Guideline Management (Phase 3)

Administrators can, from the sidebar:

- **Guidelines** -- upload a brand guideline PDF; the backend validates it, extracts text per page with PyMuPDF, splits it into ~800-1200 character chunks (with overlap) stored in `guideline_chunks`, and shows upload/processing status. Deleting a document removes its stored file and all its chunks.
- **Facts** -- CRUD for `brand_facts`, with an optional link to an uploaded guideline document (page + verbatim supporting quote). Nothing is auto-validated yet -- that's Phase 6.
- **Terminology** -- CRUD for approved terms vs. their restricted variants.
- **Claim Policies** -- CRUD for claim patterns marked allowed / needs-evidence / restricted.
- **Assets** -- logo upload (PNG/JPG/SVG, content-sniffed, SVGs rejected if they contain script-like markup) and brand colour palette management.

Uploaded PDFs and logos are stored under `backend/storage/` (`guidelines/`, `assets/`) using filenames generated from their MongoDB id -- never the original filename -- and that directory is gitignored. A demo guideline PDF matching the seeded Nova Electronics data lives at `backend/demo-assets/nova_electronics_brand_guidelines.pdf` (generated by `backend/scripts/generate_demo_pdf.py`) and is meant to be uploaded through the Guidelines page to see the pipeline work end-to-end.

Every database operation is scoped to the active organisation from the demo context above -- a request for one organisation's data can never read, update, or delete another organisation's records.

## Stack

- **Frontend:** React + TypeScript + Tailwind CSS (Vite)
- **Backend:** Python 3.11 + FastAPI
- **Database:** MongoDB
- **Document processing:** PyMuPDF
- **Image processing:** OpenCV
- **Deployment:** Docker / docker-compose

## Running locally

```bash
docker compose up --build
```

- Frontend: http://localhost:5173
- Backend: http://localhost:8000/health
- MongoDB: localhost:27018 (mapped to avoid clashing with other local Mongo instances)

## Running without Docker

Backend:
```bash
cd backend
python -m venv venv
./venv/Scripts/activate   # or source venv/bin/activate on macOS/Linux
pip install -r requirements.txt
cp .env.example .env      # adjust MONGODB_URI if needed
uvicorn app.main:app --reload
```

Frontend:
```bash
cd frontend
npm install
npm run dev
```

Seed demo data (Nova Electronics) and regenerate the demo guideline PDF, both from `backend/`:
```bash
./venv/Scripts/python.exe -m app.seed
./venv/Scripts/python.exe scripts/generate_demo_pdf.py
```
